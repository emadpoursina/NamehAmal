# Testing Standards

## Overview

No automated test framework is currently configured in this project. The app is local-first and verified manually via the dev server and the documented `curl` API examples in the README. When automated tests are introduced, prefer Vitest for unit/logic tests and keep a real (or temp) SQLite DB for data-layer tests.

## Testing Framework

**Framework**: Not configured (recommend Vitest when adopted)
**Runner**: None currently

## Test Types

| Type | Tool | Location | When to Use |

## Coverage Requirements

**Target**: Not enforced (no framework configured)
**Enforcement**: None

**Critical paths that MUST have coverage (once tests are added):**
- Live timer start → stop → finalized `Session` lifecycle
- Session `occurredAt` / duration derivation for MANUAL vs TIMER kinds
- Timezone normalization against `AppSettings.timeZone`
- Stats date-range defaulting (current week Monday–Sunday) when `from`/`to` missing
- Category uniqueness constraint and archive filtering

## Test Naming

**Pattern**: `describes "<unit>" → it("<expected behavior>")` (or `test("<expected behavior>")`)

**Examples**:
- `it("finalizes a TIMER session with endedAt on stop")`
- `it("defaults to current week when from/to are missing")`
- `it("rejects duplicate category names with 409")`

## Test Structure

```typescript
import { describe, it, expect } from "vitest";

describe("formatDuration", () => {
  it("formats seconds as H:MM:SS", () => {
    expect(formatDuration(3661)).toBe("1:01:01");
  });
});
```

## Mock Strategy

**Approach**: Prefer real dependencies over mocks. For data-layer tests, use a throwaway SQLite file (or Prisma's test DB) instead of mocking Prisma. Mock external boundaries only (e.g. `NextRequest` construction).

**Guidelines**:
- Do not mock Prisma — use a real temp SQLite DB
- Construct `NextRequest` manually for route handler tests
- Avoid mocking time; inject a clock function where needed

## Test Data

**Strategy**: Use `prisma/seed.ts` as a reference for realistic fixtures; create isolated test DBs per run.

**Guidelines**:
- Each test run gets a fresh SQLite file (e.g. `file:./test.db`), removed after
- Reuse seed helpers for consistent categories/sessions
- Never point tests at `dev.db`

## Running Tests

```bash
# Run all tests (once configured)
bunx vitest run

# Run with coverage
bunx vitest run --coverage

# Run specific test file
bunx vitest path/to/file.test.ts

# Run in watch mode
bunx vitest
```

CI/CD integration not configured. When added, run `bunx prisma migrate deploy` against a test DB, then `bunx vitest run` as a required gate.
